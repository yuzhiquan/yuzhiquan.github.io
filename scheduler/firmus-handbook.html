Part A · kube-scheduler 内核（必考底座）

Part A · kube-scheduler internals (the foundation they will test)

先立职责边界：kube-scheduler 只做一件事——为 .spec.nodeName 为空的 Pod 选一个 Node 并写回绑定，不运行容器、不保证 Pod 真能起来。ResourceQuota 是 admission 的事，LimitRange 默认值是 admission 的事，Node 故障驱逐是 node-lifecycle controller + kubelet 的事。记住这张边界表，能避开一半送命题。

🇬🇧 English Start with the boundary: kube-scheduler does one thing — pick a Node for a Pod with empty .spec.nodeName and write the binding back. It doesn't run containers or guarantee the Pod starts. ResourceQuota and LimitRange defaults are admission's job; node-failure eviction belongs to the node-lifecycle controller + kubelet. Memorize this boundary table — it defuses half the trap questions.
Q · 一次完整调度循环（scheduleOne）的数据流是什么？
Q (EN) · Walk me through one full scheduling cycle (scheduleOne).
NextPod() 从队列 pop → 获取 Node 快照 → PreFilter（任一失败即整体失败）→ findNodesThatFitPod（并发跑 Filter，percentageOfNodesToScore 提前停止）→ 若候选为空跑 PostFilter（DefaultPreemption 抢占）→ 单候选走快路径 → PreScore → Score（并发）→ NormalizeScore → 加权求和 → assume(Reserve) → Permit → 异步 Bind。一个 profile = 一个 goroutine 串行跑。
🇬🇧 NextPod() pops → Node snapshot → PreFilter (any failure fails the cycle) → findNodesThatFitPod (Filter in parallel, early stop at percentageOfNodesToScore) → if no candidates, PostFilter (DefaultPreemption) → single-candidate fast path → PreScore → Score (parallel) → NormalizeScore → weighted sum → assume(Reserve) → Permit → async Bind. One profile = one goroutine running serially.
Q · Scheduling Framework 有哪些扩展点？（必考，13 个）
Q (EN) · What extension points does the Scheduling Framework have? (13 — must know)
队列阶段 PreEnqueue / QueueSort；调度周期 PreFilter / Filter / PostFilter / PreScore / Score / NormalizeScore / Reserve；绑定周期 Permit / PreBind / Bind / PostBind；另有 Unreserve 回滚。注意：v1.19 经典列表是 12 个，新增 PreEnqueue 后为 13 个；EnqueueExtension / QueueingHint 是接口/回调，不是扩展点；multiPoint 只是配置简写，不算扩展点。
🇬🇧 Queue phase: PreEnqueue / QueueSort; scheduling cycle: PreFilter / Filter / PostFilter / PreScore / Score / NormalizeScore / Reserve; binding cycle: Permit / PreBind / Bind / PostBind; plus Unreserve rollback. Note: the v1.19 classic list was 12; with PreEnqueue it's 13; EnqueueExtension / QueueingHint are interfaces/callbacks, not extension points; multiPoint is only a config shorthand.
Q · 三级队列与抢占的关键事实？
Q (EN) · Key facts about the three queues and preemption?
ActiveQ / BackoffQ / UnschedulableQ；UnschedulableQ 靠集群事件 + podMaxInUnschedulablePodsDuration 兜底重排（QueueingHint 决定事件是否重新入队）。抢占只对“Filter 全失败”生效；nominatedNodeName 是预约不是绑定；PDB 会压制抢占；默认优先级应设 preemptionPolicy: Never 防抢占风暴。调度只看 requests，不看 limits。
🇬🇧 ActiveQ / BackoffQ / UnschedulableQ; UnschedulableQ is retried by cluster events plus the podMaxInUnschedulablePodsDuration backstop (QueueingHint decides whether an event re-enqueues). Preemption only runs when Filter fails for all nodes; nominatedNodeName is a reservation, not a binding; PDBs suppress preemption; the default PriorityClass should set preemptionPolicy: Never to avoid storms. Scheduling looks at requests, not limits.
Q · 大规模下怎么定位瓶颈？怎么优化？
Q (EN) · How do you localise a bottleneck at scale, and optimise?
三步定位法：① scheduler 插件耗时 scheduler_framework_plugin_duration_seconds；② 到 apiserver 的 apiserver_request_duration_seconds；③ etcd 的 etcd_request_duration_seconds / wal_fsync。若①高②③正常 → scheduler 算法/规模问题。优化第一银弹是节点池化（taint+label 缩小候选集 N），第二才是 percentageOfNodesToScore（牺牲最优性）；再叠加多 profile 拆分、APF 给 scheduler 专用 FlowSchema。
🇬🇧 Three-step localisation: (1) scheduler plugin duration scheduler_framework_plugin_duration_seconds; (2) apiserver_request_duration_seconds; (3) etcd_request_duration_seconds / wal_fsync. If (1) is high and (2)(3) normal → scheduler algorithm/scale problem. First optimisation silver bullet is node pooling (taint+label to shrink candidate set N), second is percentageOfNodesToScore (sacrifices optimality); then multi-profile splitting and an APF FlowSchema reserved for the scheduler.

Part B · Volcano: job-level scheduling and plugin system

Volcano 是 CNCF 旗下首个也是唯一的官方容器批处理调度项目。本质：k8s 调度的是“一个个 Pod”，Volcano 调度的是“一组组作业 + 一层层队列”。它把批处理领域完整语义（作业、队列、公平、抢占回收、拓扑）搬进调度器。核心是 Session + Action + Plugin 三层架构。

🇬🇧 English Volcano is CNCF's first and only official container batch-scheduling project. Essence: Kubernetes schedules Pods one by one; Volcano schedules groups of jobs and layers of queues. It moves the full batch semantics (job, queue, fairness, preemption/reclaim, topology) into the scheduler. The core is a three-layer Session + Action + Plugin architecture.
Q · Volcano 与 kube-scheduler 最大的架构区别？
Q (EN) · Biggest architectural difference from kube-scheduler?
原生是按 Pod 逐个决策，每个 Pod 独立走 Filter/Score/Bind，不知道兄弟在哪。Volcano 是作业级：自己的 volcano-scheduler 维护 cache + Session，OpenSession 把 pending Pod 按 PodGroup 聚成 Job 快照，按顺序跑 Actions（enqueue→allocate→preempt→reclaim→backfill），CloseSession 才绑定。关键是全局视角——提交前先判断“整组能不能满足”，这是 gang、公平、拓扑的前提。
🇬🇧 Native makes per-Pod decisions — each Pod runs Filter/Score/Bind independently with no awareness of siblings. Volcano is job-level: its own volcano-scheduler maintains a cache + Session; OpenSession snapshots pending Pods into Jobs by PodGroup, runs Actions in order (enqueue → allocate → preempt → reclaim → backfill), and only CloseSession binds. The key is a global view — decide 'can the whole group be satisfied' before committing. That's the prerequisite for gang, fairness and topology.
Q · Session / Action / Plugin 三层各自负责什么？
Q (EN) · What do the three layers Session / Action / Plugin own?
Session 承载一个调度周期：周期驱动而非事件驱动，每个周期从 Cache 拉一致性快照，基于同一份“事实”决策，结束统一提交——这是 Gang 原子性的前提。Action 定义“做什么”（5 个：enqueue/allocate/preempt/reclaim/backfill；recycle 已不是标准 Action）。Plugin 定义“怎么做”：实现 Name()/OnSessionOpen(ssn)/OnSessionClose(ssn)，在 OnSessionOpen 把算法函数注册到 Session 的扩展点（Fn map），Action 执行时回调。默认 actions 常为 enqueue, allocate, backfill，enqueue 与 preempt/reclaim 通常不同时启用。
🇬🇧 Session owns one scheduling cycle: period-driven, not event-driven — each cycle pulls a consistent snapshot from Cache, decides on one 'fact', and commits at the end; that's the prerequisite for gang atomicity. Action defines 'what' (five: enqueue/allocate/preempt/reclaim/backfill; recycle is no longer standard). Plugin defines 'how': implement Name()/OnSessionOpen(ssn)/OnSessionClose(ssn), register algorithm functions onto Session extension points (Fn maps) in OnSessionOpen, called back during Actions. Default actions are usually enqueue, allocate, backfill; enqueue and preempt/reclaim are normally not enabled together.

B.1 扩展点四大类（20+ 个 Fn）与 gang 实现

B.1 Four categories of extension points (20+ Fns) and gang implementation

  • 四大类：① 排序 Ordering（jobOrderFn/queueOrderFn/taskOrderFn/nodeOrderFn/batchNodeOrderFn…）；② 过滤与准入 Validation（predicateFn/jobValidFn/jobReadyFn/jobStarvingFn…）；③ 抢占与回收（preemptableFn/reclaimableFn/victimTasksFn/overusedFn…）；④ 状态与预留（reservedNodesFn/targetJobFn/jobPipelineFn）。同一 Fn 可被多插件注册，靠 tier 顺序组合。
    🇬🇧 Four categories: (1) Ordering (jobOrderFn/queueOrderFn/taskOrderFn/nodeOrderFn/batchNodeOrderFn…); (2) Validation (predicateFn/jobValidFn/jobReadyFn/jobStarvingFn…); (3) Preempt/Reclaim (preemptableFn/reclaimableFn/victimTasksFn/overusedFn…); (4) State/Reserve (reservedNodesFn/targetJobFn/jobPipelineFn). The same Fn can be registered by several plugins, composed by tier order.
  • gang 实现：PodGroup 的 minMember + gang 插件的 JobReady = (allocated + pipelined) ≥ minMember。allocate 阶段未达 minMember 就不绑定——等待；suicide 插件超时释放整组避免死锁。占坑（jobPipelineFn）是原子性的关键。
    🇬🇧 Gang: PodGroup minMember + gang plugin's JobReady = (allocated + pipelined) ≥ minMember. In allocate, if minMember isn't met the job isn't bound — it waits; the suicide plugin releases the whole job on timeout to avoid deadlock. Pipelining (jobPipelineFn) is the key to atomicity.
  • preempt vs reclaim：preempt 同队列内按优先级抢占；reclaim 跨队列按权重把借出的应得份额收回——两个独立 Action，各管一层。conformance 插件保护 kube-system 关键 Pod。
    🇬🇧 preempt vs reclaim: preempt takes from lower priority within a queue; reclaim recovers lent-out entitled share across queues by weight — two independent Actions, each one layer. The conformance plugin protects kube-system Pods.
  • 拓扑与设备：task-topology 按通信关系把频繁通信的 Task 共置同一 NVLink 域/leaf switch；numaaware 对齐 CPU/内存到 GPU 的 NUMA；deviceshare 支持 GPU 共享/MIG/vCUDA。到 NVL72：层级换成 rack（单一 NVLink 域）→ 液冷回路/PDU → node。
    🇬🇧 Topology & devices: task-topology co-locates chatty Tasks in the same NVLink domain / leaf switch; numaaware aligns CPU/memory to the GPU's NUMA node; deviceshare supports GPU sharing / MIG / vCUDA. On NVL72 the levels become rack (single NVLink domain) → cooling loop / PDU → node.

B.2 三种扩展方式（从易到难）

B.2 Three ways to extend (easy to hard)

  • A 配置内置插件：ConfigMap 的 tiers 增减/排序插件，零代码改行为（首选）；B Extender：HTTP 回调外部服务，钩子最全、可跨语言，无需重编译，但每次调度 HTTP 串行阻塞、挂了会卡调度，需超时+降级；C 自定义 Plugin：实现接口 + RegisterPluginBuilder，编译进调度器。
    🇬🇧 A configure built-in plugins: add/reorder plugins in the ConfigMap's tiers, zero code (first choice); B Extender: HTTP callback to an external service, most hooks, cross-language, no recompile — but every scheduling cycle blocks on HTTP and a down extender stalls scheduling, so add timeout + degradation; C custom Plugin: implement the interface + RegisterPluginBuilder, compile into the scheduler.
中文 口径红线：Kueue 不是“不支持 gang”，而是作业级 vs 调度级。常见三方对比表写 “Kueue gang = ❌” 在 2024 年前大致成立，现已过时——准确说法见 §6。
🇬🇧 Red-line phrasing: Kueue does not 'lack gang' — it's job-level vs scheduling-level. Third-party comparison tables saying 'Kueue gang = ❌' were roughly true before 2024 and are now outdated — see §6 for the accurate statement.

Part C · Kueue：准入、配额与治理

Part C · Kueue: admission, quota and governance

Kueue 不是 Pod 调度器，而是准入 + 配额 + 公平 + 抢占系统，不替换 kube-scheduler。流程：提交 Job → Kueue 创建 Workload（Pending）→ 准入阶段决定“准不准/给多少/哪个 flavor” → Admitted=true 后把资源请求 patch 回 Pod → kube-scheduler 负责放置。一句话：Kueue 决定“能不能”，kube-scheduler 决定“放哪儿”。价值是把“调度之前的治理”产品化。

🇬🇧 English Kueue is not a Pod scheduler but an admission + quota + fairness + preemption system that doesn't replace kube-scheduler. Flow: submit Job → Kueue creates a Workload (Pending) → admission decides 'admit or not / how much / which flavor' → once Admitted=true it patches resource requests back onto Pods → kube-scheduler does placement. One-liner: Kueue decides 'whether', kube-scheduler decides 'where'. Its value is productising 'governance before scheduling'.

C.1 核心对象与配额模型

C.1 Core objects and quota model

  • 六类核心对象：ResourceFlavor（资源“口味”，如 gpu-h100-nvl72，带 selector/taint 与 topologyName）；ClusterQueue CQ（配额主体：resourceGroups、cohort 借用、抢占、admissionChecks、namespaceSelector）；LocalQueue LQ（namespace 级，指向 CQ，Job 打 queue-name 标签进入）；Workload（由 Job 生成，记录 podSets 与 status.admission）；AdmissionCheck（准入闸门）；Topology/TAS（拓扑感知）。
    🇬🇧 Six core objects: ResourceFlavor (resource 'flavour', e.g. gpu-h100-nvl72, with selector/taint and topologyName); ClusterQueue CQ (quota subject: resourceGroups, cohort borrowing, preemption, admissionChecks, namespaceSelector); LocalQueue LQ (namespace-scoped, points to a CQ, Jobs label queue-name to enter); Workload (generated from the Job, records podSets and status.admission); AdmissionCheck (admission gate); Topology/TAS (topology-aware scheduling).
  • 配额与借用：CQ 有 nominalQuota；cohort 内互相借用（borrowingLimit 上限，lendingLimit 控制借出）；借出方来高优先级作业时 reclaim/preempt 收回。公平用 cohort 内 DRS（Dominant Resource Share）。抢占三个开关默认都是 Never：withinClusterQueue / reclaimWithinCohort / borrowWithinCohort。FlavorFungibility 让首选 flavor 满时回退到可互换的。
    🇬🇧 Quota & borrowing: a CQ has nominalQuota; CQs in a cohort borrow from each other (borrowingLimit cap, lendingLimit controls lending); when the lender gets a high-priority job, reclaim/preempt recovers it. Fairness uses DRS (Dominant Resource Share) inside the cohort. Three preemption knobs all default Never: withinClusterQueue / reclaimWithinCohort / borrowWithinCohort. FlavorFungibility lets a full preferred flavour fall back to an interchangeable one.
  • Job → Workload 生成靠 PodSets 抽象：把不同框架（Job/JobSet/PyTorchJob/RayJob）的差异用 PodSets() 抹平，调度只认统一结构。配额用量 = Σ(podSet 请求 × count)。新增框架只需实现 manager 接口。
    🇬🇧 Job → Workload uses the PodSets abstraction: differences across frameworks (Job/JobSet/PyTorchJob/RayJob) are flattened by PodSets(); scheduling only sees a uniform structure. Quota usage = Σ(podSet requests × count). Adding a framework only needs a manager implementation.

C.2 gangs、TAS 与 AdmissionCheck（Firmus 杀手锏）

C.2 Gangs, TAS and AdmissionCheck (the Firmus killer feature)

  • Kueue 的 gang = 准入层 all-or-nothing：每个 podSet 必须在 Admitted 前同时满足配额 + TAS 域；All-or-nothing with PodsReady 在 podsReadyTimeout 内未全部 Ready 就驱逐 + 指数退避重排；podSets[].minCount 允许部分；另有 Partial Admission 与 Dynamic Reclaim。它比 Volcano 运行时拼装失败得更早、释放得更快。
    🇬🇧 Kueue's gang = admission-level all-or-nothing: every podSet must fit quota + TAS domain before Admitted; All-or-nothing with PodsReady evicts and requeues with exponential backoff if not all Ready within podsReadyTimeout; podSets[].minCount allows partial; plus Partial Admission and Dynamic Reclaim. It fails earlier and releases faster than Volcano's runtime assembly.
  • TAS 精确机制（口语“整域预留”的准确版本）：定义 Topology CRD（层级如 rack→block→node，每层按域打标签），ResourceFlavor 引用它；在 PodTemplate 上用 podset-required-topology / preferred / unconstrained 等注解逐层评估；准入时只选能完整填满的域、域间互斥避免碎片，然后 kube-scheduler 在域内放置。NVL72 的 rack（单一 NVLink 域）天然是 TAS 顶层，液冷回路/PDU 为附加层。
    🇬🇧 TAS precise mechanism (the accurate version of the colloquial 'whole-domain reservation'): define a Topology CRD (levels like rack→block→node, each labelled by domain), referenced by a ResourceFlavor; use podset-required-topology / preferred / unconstrained annotations on the PodTemplate evaluated level by level; at admission only pick a domain that can be completely filled, domains are mutually exclusive to avoid fragmentation, then kube-scheduler places inside the domain. The NVL72 rack (single NVLink domain) is naturally the top TAS level, with cooling loop / PDU as extra levels.
  • AdmissionCheck = 可插拔准入闸门：所有 check state=Ready 前 Workload 不被 Admitted。写自定义 controller 设状态。AI FactoryOS 的功耗/热/电网/维护信号恰好就是一个 AIFactoryAdmissionCheck：电价高峰、热降额、维护窗口 → Pending → 不准入。这是接外部遥测最干净的扩展点，比改调度器内核优雅十倍。
    🇬🇧 AdmissionCheck = a pluggable admission gate: a Workload isn't Admitted until all checks report state=Ready; you write a custom controller to set the state. AI FactoryOS's power/thermal/grid/maintenance signals are exactly an AIFactoryAdmissionCheck: peak price, thermal derate, maintenance window → Pending → not admitted. It's the cleanest extension point for external telemetry — ten times more elegant than hacking the scheduler core.
  • 可见性 = Workload 的 status.conditions（Admitted/Pending/Preempted/Finished）+ events + Prometheus 指标（队列深度/准入等待/抢占数）——这就是 JD 里的“可执行的调度解释”。MultiKueue 做多集群；TAS/DRA/Topology Spreading 等新特性以较新版本为准，面试统一说“我讲机制，具体状态以部署版本为准”。
    🇬🇧 Visibility = Workload status.conditions (Admitted/Pending/Preempted/Finished) + events + Prometheus metrics (queue depth / admission wait / preemptions) — that's the JD's 'actionable scheduler explanations'. MultiKueue handles multi-cluster. For TAS/DRA/Topology Spreading say 'I explain the mechanism; status depends on the deployed version'.
中文 DRA 注意：device plugin 只报“本地几张卡”，对 NVLink 拓扑/整机架一无所知；DRA（DeviceClass + 结构化参数）让调度器看到“哪个 NVLink 域、与哪些卡互联”，是 NVL72 拓扑感知的前提。DRA 不支持 Pod 抢占。
🇬🇧 DRA note: the device plugin only reports 'how many cards locally', blind to NVLink topology / whole-rack; DRA (DeviceClass + structured params) lets the scheduler see 'which NVLink domain, interconnected with which cards' — the prerequisite for NVL72 topology awareness. DRA does not support Pod preemption.

D.1 Gang 三层级（高频追问）

D.1 Three levels of gang (frequent follow-up)

  • K8s 原生 Coscheduling：kube-scheduler 插件，2024 起 beta 演进，纯原生、能力基础。
    🇬🇧 K8s-native Coscheduling: a kube-scheduler plugin, beta since 2024, pure native and fairly basic.
  • Kueue 准入层：Workload 整体准入 + All-or-nothing with PodsReady；不保证所有 Pod 同一时刻被原子绑定，但保证配额与作业整体放行。
    🇬🇧 Kueue admission-level: Workload admitted as a whole + All-or-nothing with PodsReady; doesn't guarantee all Pods are atomically bound at the same instant, but guarantees quota and whole-job release.
  • Volcano 调度层：PodGroup + minMember + jobPipelineFn 占坑，凑齐后统一绑定——严格调度级 gang。追求严格 gang 时 Volcano 更强，重视原生集成与配额治理时 Kueue 更省心。
    🇬🇧 Volcano scheduling-level: PodGroup + minMember + jobPipelineFn pipelining, bind together once assembled — strict scheduling-level gang. Volcano is stronger for strict gang; Kueue is easier when you value native integration and quota governance.

D.2 选型决策树与常见误区

D.2 Selection decision tree and common misconceptions

  • 小团队先跑稳 → 原生 kube-scheduler + namespace；多团队要配额公平 → Kueue；分布式训练要严格 Gang/Backfill → Volcano；两者都要 → Kueue 准入 + Volcano 调度组合。
    🇬🇧 Small team, get stable first → native kube-scheduler + namespace; multi-team needing quota/fairness → Kueue; distributed training needing strict gang/backfill → Volcano; both → Kueue admission + Volcano scheduling composition.
  • 经验法则（Jimmy Song《AI 基础设施手册》）：Kueue 更像资源治理框架（准入+配额+承诺+统计），是平台底座；Volcano 更像批处理调度引擎，是训练负载加速器。
    🇬🇧 Rule of thumb (Jimmy Song, AI Infrastructure Handbook): Kueue is more a resource-governance framework (admission+quota+commitment+accounting), the platform base; Volcano is more a batch scheduling engine, the training-workload accelerator.
  • 误区纠正：①“Kueue 不支持 Gang”已过时；②“Kueue 替代 kube-scheduler”错；③“用了 Volcano 就不需要配额治理”不一定；④“两者只能二选一”错，正交可组合。
    🇬🇧 Misconceptions corrected: (1) 'Kueue has no gang' is outdated; (2) 'Kueue replaces kube-scheduler' is wrong; (3) 'Volcano means no quota governance needed' — not necessarily; (4) 'pick only one' is wrong — they compose orthogonally.

Part E · 协同：Kueue + Volcano 正交组合

Part E · Composition: Kueue + Volcano, orthogonal by design

两者能配合的根本原因：作用在作业生命周期不同阶段，职责不重叠。Kueue 决定“谁能进场、能占多少、何时放行”（准入、配额、承诺、统计），Volcano 决定“怎么排座位、放在哪”（作业级调度、Gang、抢占回收）。形成“先治理、再调度”的闭环。这正是 JD 的 “integrate … rather than replace”。

🇬🇧 English They compose because they act at different lifecycle stages with non-overlapping duties. Kueue decides 'who enters, how much, when released' (admission, quota, commitment, accounting); Volcano decides 'how to seat and where to place' (job-level scheduling, gang, preemption/reclaim). Together they close the loop 'govern first, schedule second' — exactly the JD's 'integrate … rather than replace'.

E.1 组合架构：数据平面 + 控制面

E.1 Composition architecture: data plane + control plane

  • 数据平面（资源单位与隔离）：整卡 nvidia.com/gpu / MIG 硬切分 / 共享虚拟化（HAMi 等）。控制面（秩序与策略）：Kueue（治理/准入/配额/承诺/统计）+ Volcano（批处理语义/调度策略）。平台层：门户、训练生命周期、SLO、计量。
    🇬🇧 Data plane (resource unit & isolation): whole GPU nvidia.com/gpu / MIG hard partition / shared virtualisation (HAMi). Control plane (order & policy): Kueue (governance/admission/quota/commitment/accounting) + Volcano (batch semantics/scheduling policy). Platform layer: portal, training lifecycle, SLO, metering.
  • 分工边界表：配额准入与统计以 Kueue 为单一事实源；调度策略与 gang 以 Volcano 为准。两者都有队列与抢占——这是最大重叠风险，须避免策略重复/互相打架。
    🇬🇧 Division of labour: quota admission and accounting take Kueue as the single source of truth; scheduling policy and gang take Volcano as authoritative. Both have queues and preemption — the biggest overlap risk; avoid duplicated or conflicting policy.
  • 协同生命周期：提交挂起(suspend:true) → Kueue 配额准入 → 解除挂起 → Pod 由 schedulerName=volcano 接管做 gang + 放置 → 运行/抢占 → 完成归还配额。交接靠 suspend 状态 + schedulerName 衔接。
    🇬🇧 Lifecycle: submit + suspend:true → Kueue quota admission → unsuspend → Pods taken over by schedulerName=volcano for gang + placement → run/preempt → finish and return quota. The handoff is via suspend state + schedulerName.
