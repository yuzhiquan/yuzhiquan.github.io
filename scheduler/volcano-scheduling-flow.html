🗂️0.1 管理员预建 Queue（CRD）

安装后内置 root（根队列）与 default（默认队列，weight=1），均不可删改。其余按业务自建。核心是三级配额模型：guarantee ≤ deserved/weight ≤ capability。

# scheduling.volcano.sh/v1beta1
apiVersion: scheduling.volcano.sh/v1beta1
kind: Queue
metadata: {name: training}
spec:
  deserved:            # 软基准（capacity 插件用）
    cpu: "16"; nvidia.com/gpu: "8"
  guarantee:           # 硬下限，独占预留
    resource: {cpu: "8", nvidia.com/gpu: "2"}
  capability:          # 硬上限，绝对封顶
    cpu: "32"; nvidia.com/gpu: "16"
  weight: 1            # 比例权重（proportion 插件用）
  priority: 100
  reclaimable: true
  state: Open
注意：capacity（配 deserved）与 proportion（配 weight）二选一，不能同时用；只有 state=Open 才能接收任务。
📦0.2 用户提交 VCJob（作业，不是散装 Pod）

提交类型是作业 Job，层级在提交时就定义好。顶层 spec.queue 声明归属（不写则进 default）。

# batch.volcano.sh/v1alpha1
apiVersion: batch.volcano.sh/v1alpha1
kind: Job
metadata: {name: pytorch-ddp}
spec:
  queue: training        # ← 归属队列（声明式）
  minAvailable: 4        # ← gang 门槛 → PodGroup.MinMember
  tasks:
    - name: worker
      replicas: 4        # ← 生成 4 个 Pod
      template:
        spec:
          schedulerName: volcano   # ← 交给 volcano
          containers: [...]
其他框架（PyTorchJob / MPIJob 等）无 spec.queue，改用注解： metadata.annotations.scheduling.volcano.sh/queue-name: training + spec.schedulingPolicy.{queue,minAvailable}。

⚙️0.4 调度器配置（ConfigMap）

定义 Action 执行顺序与插件分层（tier）。同一扩展点被多插件注册时，靠 tier 顺序组合结果。

actions: "enqueue, allocate, preempt, reclaim, backfill"
tiers:
  - plugins:            # 第一层：排序 / 准入
      - {name: priority}
      - {name: gang}
      - {name: hwtopology}   # 自定义硬件插件
  - plugins:            # 第二层：过滤 / 打分
      - {name: drf}
      - {name: predicates}
      - {name: nodeorder}
      - {name: binpack}
默认配置常为 enqueue,allocate,backfill；enqueue 与 preempt/reclaim 通常不同时启用（见阶段 4）。
✅ 准入校验：提交后准入组件检查队列是否存在、state 是否 Open；启用分层队列时还要求是叶子节点。校验不过直接拒绝。

wait.Until 在单个 goroutine 同步调用 runOnce：不会有两个 Session 并发。Session 内部也是串行执行各 Action，全程共用同一个 ssn。

⏱️跑完再等 1 秒（sliding）

🚪4.1 enqueue 入队

过滤任务，状态 pending → inqueue。用 jobEnqueueableFn 检查队列配额与 gang 最小资源，不满足的 Job 不生成 Pending Pod。

⚡4.3 preempt 抢占

输入 = allocate 后仍饥饿的 Job（JobStarving）。限定同队列内选低优先级 victim，Evict + Pipeline 放同一 Statement 事务，达到 JobPipelined 才整体 Commit。

🔄4.4 reclaim 回收

与 preempt 同构，区别在于 victim 来自其他队列（按权重收回借出的份额），涉及租户边界，是更重的操作故后置。

🧠4.2 allocate —— 核心中的核心（展开）

用空闲资源、按「队列 → 作业 → 任务」层级做预选 + 优选，gang 满足才 Commit，否则整体 Discard —— 全程不驱逐任何 Pod。

① 准备：buildAllocateContext（筛选谁有资格）

跳过 pending / JobValid 不通过 / 被 unschedulable 抑制 / 队列不存在的 Job；organizeJobWorksheet 分 nominated（上轮抢占锁定）与 regular 两阶段；无资源请求的 task 直接跳过，留给 backfill。

优选两梯度：① Idle 就够用的节点优先打分，有结果就不看第二梯度；② FutureIdle（Idle+Releasing−Pipelined）才够用的节点作为后备。

💾扣资源 ≈ Reserve（但非扩展点）

node.AddTask() 改 NodeInfo 记账：Idle.sub() / Used.Add()；Pipeline 则加 Pipelined 使 FutureIdle 变小。仅内存记账，防本轮重复占用，Session 结束即丢弃；gang 不过则 Discard 反向回滚。K8s 的 Reserve 是独立 stage，Volcano 直接改字段更内聚。

🎯决策单位 = PodGroup

一轮 allocate 处理多个 PodGroup（training 的 A、B，default 的 C…逐个），但每次决策的单位是一个组：组内逐个 Pod 选节点（执行单位）却不立即绑定，整组记入同一 Statement，整组 Commit / Discard。整体判定保 gang，逐 task 记账保执行粒度。

◆ 判定：ssn.JobReady(job) ？ 该 Job 是否满足 minAvailable（全有 or 全无）
✅ 满足 → stmt.Commit()

整组 Operation 一起提交 → 进入阶段 5 转为 BindTask。8 个 Pod 全部分配。

❌ 不满足 → Discard

整组回滚，一个都不占 —— 这正是 Gang 死锁不再发生的机制。饥饿 Job 留给 preempt/reclaim。

allocate 不做什么同样重要：不写 API Server（只内存决策 + 记账）；不驱逐任何 Pod（Statement 只有 Pipeline/Allocate）。高级细节：NominatedNodeName 优先、HyperNode 拓扑、shard 分片、FitErrors 追踪。
🧩4.5 backfill 回填（必须垫底）

pickUpPendingTasks() 多重过滤：if job.IsPending() continue / JobValid 不通过跳过 / if task.HasSchedulingResourceRequests() continue（只留无资源请求的 BestEffort）/ scheduling gate 跳过。它用的是前面 Action 更新后的剩余碎片资源。

为什么垫底：它跳过 gang 与配额核算，若放前面会先占住节点、把正经作业挤掉，破坏公平与 gang 整体性。放最后才能"只利用别人不要的边角料"。

🍽️附录 C · Gang 通俗理解与决策单位小结
Gang 三招（"8 人聚餐订位"）

① 绑成一单：PodGroup + minAvailable:8，调度器眼里是一个整体。
② 先看全貌：拍资源快照，看清总共剩几张卡。
③ 凑不齐全撤回：内存试算，JobReady 通过才 Commit；不够 Discard 全撤回，一个不占。因在内存里，撤回不留痕迹。

对比 K8s：先起的 4 个占卡死等同伴 → 后 4 个永远起不来 → 全体卡死、GPU 白占。Volcano 从根上杜绝"半组卡死"。
allocate 决策单位 = PodGroup

一轮 allocate 会处理多个 PodGroup，但每次拿出来决策的单位是一个组：
• 决策判定 → 一个 PodGroup（JobReady）
• 节点选点 → 单个 Pod（predicate + nodeOrder）
• 结果提交 → 一个 PodGroup（同一 Statement 一起提交）

"一次遍历多组、逐个组决策" —— 组 A 凑不齐就回滚 A，不影响组 B。
