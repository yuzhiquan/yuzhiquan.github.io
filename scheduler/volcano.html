摘要

Volcano 是 CNCF 旗下首个、也是目前唯一的官方容器批处理调度项目。它把批处理领域的完整语义——作业（Job/PodGroup）、队列（Queue）、公平、抢占回收、拓扑感知——搬进了 Kubernetes 调度器。本文从「调度单元错配」这一根源出发，系统拆解 Volcano 的 Session + Action + Plugin 三层架构、调度全流程、插件扩展点体系，并补齐核心对象实战、关键策略配置、GPU/拓扑感知与生产排障，最后给出与 kube-scheduler 的深度对比和选型建议。

阅读约定：本文在原《Volcano 调度器原理详解》基础上扩展了实战、策略配置、GPU 与生产章节。涉及 API 与特性以 Volcano v1.9+ / v1.10+ 为准；部分高级特性（如动态 MIG、volcano-global 多集群）的成熟度已在文中标注，落地前请核对目标版本文档。

0. 为什么需要 Volcano：问题与对策

理解 Volcano，先要理解它为什么存在。根源只有一句话：调度单元的错配。原生 kube-scheduler 以「单个 Pod」为单元逐个调度，这对无状态 Web 服务没问题；但批处理 / AI 训练的语义是「一组 Pod 才是一个任务」。这个错配引出五个问题，下面把每个问题与 Volcano 的对策逐条对应。

① 分布式训练「部分调度死锁」· 最核心

MPI/PyTorch DDP 需 N 个 Pod 同时启动。K8s 逐个调度：先起的 Pod 占住资源并等待通信，剩下的 Pod 因资源不足 Pending——全体卡死，谁也不释放。

→
Gang Scheduling（全有或全无）

用 PodGroup 把一组 Pod 绑成整体，minAvailable 定义最小运行数。凑不齐就一个都不调，凑齐才一起调，从根上杜绝死锁。

gang 插件 · jobValidFn / jobReadyFn / jobStarvingFn
② 多租户资源争抢、无配额

K8s 没有「作业队列」概念，Pod 直接进调度队列裸竞争。重要任务可能被海量小任务挤掉，团队之间无公平性保障。

→
多层级队列 + 配额

引入 Queue CRD（可分层），deserved/guarantee/capability 描述应得、保底、上限，按权重或显式配额分配，实现租户隔离与公平。

proportion（按权重）· capacity（显式配额）· queueOrderFn
③ 资源借还不灵活

K8s 的抢占只按 Pod 优先级，没有「跨队列回收」：A 队列借用了 B 队列的空闲资源，当 B 自己要用时却拿不回来。

→
抢占与回收分离

preempt 处理同队列内高优先级抢占；reclaim 按队列权重把「借出去」的应得份额收回来。两个独立 Action，各管一层。

preempt + reclaim Action · preemptableFn / reclaimableFn / victimTasksFn
④ 资源碎片、利用率低

默认 LeastAllocated 策略倾向把 Pod 打散，节点残留大量碎片，昂贵的 GPU 资源白白浪费。

→
装箱 + 碎片回填

binpack 把 Pod 往已用节点上紧凑堆放；backfill 用调度周期剩余碎片资源去塞 pending 的小任务，榨干每一份资源。

binpack · backfill Action · nodeOrderFn
⑤ 异构设备与拓扑感知

GPU/NPU 共享、NUMA 亲和、多机通信拓扑——AI 训练对「放在哪」极其敏感，默认调度器无能为力。

→
设备与拓扑感知插件

numaaware 考虑 CPU NUMA，deviceshare 支持 GPU 共享，task-topology / 网络拓扑感知降低跨节点通信开销。

numaaware · deviceshare · network topology aware
本质：K8s 调度的是「一个个 Pod」，Volcano 调度的是「一组组作业 + 一层层队列」。多出来的复杂度，全部服务于批处理场景的刚需：整体调度、公平配额、借还回收、高利用率、异构感知。

三个层层递进的设计支柱

① 显式建模批处理概念

用 PodGroup 把一组 Pod 绑成「作业」，用 Queue 把租户映射成「队列」——让「组」和「队列」成为调度器看得见的一等公民，而不只是外部约定。

② 周期快照 + Session

要做到「全有或全无」，必须先看到全局再一次性决策。所以 Volcano 不用事件驱动，而是每周期拉一份一致性快照，在 Session 内基于同一份「事实」做整体判断。

③ Action 时机 + Plugin 逻辑

把决策时机切细（入队/分配/抢占/回收/回填），每个时机再挂可插拔算法。扩展点之所以多，正是因为时机被切得细——这是「为什么比 K8s 多」的真正答案。

调度流程：每一步的动机

  • Cache · 准备与快照
    监听集群 → 缓存 Node / Pod / Job / Queue，拉取一致性快照。解决：分布式系统里信息难同步；用某一时刻的快照调度，保证同周期内所有决策基于同一份「事实」，不会互相打架。
  • Action 1 · enqueue 入队
    按队列配额与规则过滤 Job，状态 pending → inqueue。解决：配额准入，拦住超额作业（对应问题②多租户公平）。
  • Action 2 · allocate 分配
    队列→作业→任务层层排序，predicates 预选 + nodeorder/binpack 优选，选点绑定；凑不齐 minAvailable 则整个 Job 不调。解决：gang 全有或全无（①）、binpack 提升利用率（④）、numaaware 处理拓扑（⑤）。
  • Action 3/4 · preempt / reclaim
    preempt 同队列内高优先级抢占；reclaim 跨队列按权重回收借出的资源。解决：资源借还分两层（③），让高价值任务拿得到资源。
  • Action 5 · backfill 回填
    用本周期剩余的碎片资源，调度 pending 的小任务 / BestEffort 作业。解决：见缝插针，把利用率榨到最高（④）。
  • Apply · 提交收尾
    把本周期所有绑定/驱逐决策一次性应用到集群，关闭 Session。解决：原子性，避免「调了一半」的中间态，让调度效果可预期。

贯穿全流程的机制：每个 Action 具体怎么排序、怎么过滤、谁能抢谁，都由 Plugin 注册的扩展点回调决定——这就是 Action + Plugin 分层。

1. Volcano 是什么

Volcano 是 CNCF 旗下的、基于 Kubernetes 的高性能批处理调度引擎，也是 CNCF 首个且唯一的官方容器批处理调度项目。原生 kube-scheduler 以单个 Pod 为调度单元，难以满足 AI 训练、MPI、Spark/Flink、Ray 等场景中「一组 Pod 必须同时启动」的需求。Volcano 在 K8s 之上提供了作业级（Job/PodGroup）调度、多层级队列配额、Gang Scheduling、公平共享、抢占回收和异构设备（GPU/NPU）支持。

它的调度器 volcano-scheduler 采用高度可扩展的 Session + Action + Plugin 三层架构：每个调度周期开启一个 Session，按顺序执行多个 Action，而每个 Action 的具体算法由注册的 Plugin 提供。这种分层让调度策略完全可插拔。

A Action

定义「做什么」：enqueue / allocate / preempt / reclaim / backfill 等调度环节。

P Plugin

定义「怎么做」：通过向 Session 注册回调函数（扩展点）提供具体算法。

S Session

承载一个调度周期：基于集群快照做决策，周期结束统一提交，保证一致性。

能力全景

统一调度

支持原生 K8s 工作负载；通过 VolcanoJob 完整支持 PyTorch/TensorFlow/Spark/Flink/Ray；在线微服务与离线批处理统一调度，提升集群利用率。

丰富调度策略

Gang、Binpack、DRF、Proportion/Capacity、NodeGroup、SLA、Task-topology、NUMA-aware，以及异构设备（GPU/NPU）调度。

队列资源管理

多维资源配额（CPU/Memory/GPU）；多层级队列与资源继承；队列间借用、回收、抢占；多租户隔离与优先级。

高级能力

网络拓扑感知、在线离线混部（超卖/CPU burst）、多集群调度（volcano-global）、动态重调度（descheduler）、Dashboard 与指标。

2. 整体调度流程

Volcano 的调度决策不是事件驱动，而是周期驱动：每个周期开启一个 Session，从 Cache 拉取集群快照，遍历待调度 Job，依次执行各 Action，为 Job 找到合适节点并绑定，最后关闭 Session。

3. 插件与扩展点体系

每个 Plugin 必须实现 Name()、OnSessionOpen(ssn)、OnSessionClose(ssn) 三个方法。真正的扩展逻辑发生在 OnSessionOpen：插件在此把算法函数注册到 Session 的各类扩展点（本质是若干 Fn map），Action 执行时再回调它们。

插件接口：三个方法

Name() string

返回插件唯一名称，供 ConfigMap 配置引用。

OnSessionOpen(ssn)

每个调度周期开始时调用，在此把算法函数注册到 Session 的各个扩展点。

OnSessionClose(ssn)

会话结束时清理中间状态、更新指标。

扩展点四大类（20+ 个 Fn）

① 排序类 Ordering

jobOrderFn · queueOrderFn · taskOrderFn · nodeOrderFn · batchNodeOrderFn · bestNodeFn · namespaceOrderFn · clusterOrderFn

② 过滤与准入 Validation

predicateFn · prePredicateFn · jobEnqueueableFn · jobValidFn · jobReadyFn · jobStarvingFn

③ 抢占与回收 Preempt / Reclaim

preemptableFn · reclaimableFn · overusedFn · allocatableFn · victimTasksFn · reclaimFn

④ 状态与预留 State / Reserve

reservedNodesFn · targetJobFn · jobPipelineFn · jobEnqueuedFn · eventHandler

三种扩展方式：从易到难

A · 配置内置插件

在 ConfigMap 的 tiers 里增减/排序插件，零代码改行为。首选。

B · Extender 外部扩展

通过 HTTP 回调外部服务，钩子最全、可跨语言，无需重编译调度器。

C · 自定义 Plugin

实现 Plugin 接口 + RegisterPluginBuilder 注册，编译进自定义调度器。

机制要点：同一扩展点可被多个插件注册，结果按 tier 顺序组合——这正是默认配置分两层 plugins 的原因。例如 priority 与 gang 都注册 jobOrderFn，需靠分层顺序决定最终排序。

5. 与 K8s 官方调度器对比

Volcano 的扩展点数量（20+）明显多于 Kubernetes 官方调度框架（约 12~13 个）。但这并不是简单的「功能堆得多」，而是两种扩展模型的本质差异：官方调度器是线性流水线（Pipeline），一次只调一个 Pod，扩展点是主线上固定的阶段卡槽；Volcano 是多级决策回调（Hook），一次调一批 Job，扩展点是 Action 回调的各种决策函数。

◆ kube-scheduler · 线性流水线

一次只调一个 Pod；扩展点 = 主线上固定的「阶段卡槽」，约 12~13 个。

  • QueueSort → PreFilter → Filter → PostFilter
  • PreScore → Score → NormalizeScore
  • Reserve → Permit → PreBind → Bind → PostBind

▲ Volcano · 多级决策回调

一次调一批 Job；扩展点 = Action 回调的「决策函数」，20+ 个 Fn（四大类）。

  • jobOrderFn / queueOrderFn / taskOrderFn
  • predicateFn / jobValidFn / jobReadyFn
  • preemptableFn / victimTasksFn / reclaimableFn…

1 · 调度对象层级

K8s 只围绕 Pod 一个层级；Volcano 要同时排 Queue→Job→Task→Node 四层，每层都要排序/判断，钩子自然翻倍。

2 · 模型粒度不同

K8s 是「阶段卡槽」，一个阶段一个接口；Volcano 是「决策回调」，同类能力拆成 Order/Valid/Ready/Starving 等更细的 Fn。

3 · 功能内建范围

gang、DRF、配额、抢占回收、资源预留都是 Volcano 原生能力；K8s 多交给 out-of-tree 插件（如 Coscheduling / Kueue）。

一句话总结：K8s 用「少而固定的阶段」换取简洁，Volcano 用「多而细的回调」换取批处理场景的可控性——这是为 Gang 调度、多租户配额、抢占回收这些批处理刚需付出的复杂度代价。

6. 核心概念与 YAML 实战

三个核心对象

Job（VCJob）

Volcano 自定义 CRD，描述一个批处理作业：多个 Task、每个 Task 的副本数、生命周期策略。是对原生 Job 语义的扩展。

PodGroup

gang 调度的载体，绑定一组 Pod，声明 minMember / minTaskMember。原生 Job/Deployment 也可通过标签关联 PodGroup。

Queue

租户/队列的抽象，可分层。通过 weight 或 capability / guarantee 描述资源份额，是公平与配额的基础。

实战一：一个 Gang 调度的 VCJob

apiVersion: batch.volcano.sh/v1alpha1
kind: Job
metadata:
  name: pytorch-ddp
spec:
  minAvailable: 4            # 凑齐 4 个 Pod 才一起启动（gang）
  schedulerName: volcano
  queue: research-queue
  plugins:
    env: []
    svc: []
  tasks:
    - name: worker
      replicas: 4
      template:
        spec:
          containers:
            - name: pytorch
              image: pytorch/pytorch:2.1.0-cuda12.1-cudnn8-runtime
              command: ["python", "train.py"]
              resources:
                limits:
                  nvidia.com/gpu: 1
      policies:
        - event: PodEvicted
          action: RestartJob

minAvailable: 4 是 gang 的关键：Volcano 会为这 4 个 Pod 预留资源，凑不齐就一个都不绑定，从根本上避免「3 个 GPU 占着空等第 4 个」的死锁。

实战二：队列配额

apiVersion: scheduling.volcano.sh/v1beta1
kind: Queue
metadata:
  name: research-queue
spec:
  weight: 2                  # 按权重参与 proportion 分配
  capability:                # 资源上限
    nvidia.com/gpu: "16"
    cpu: "64"
  guarantee:                 # 保底份额（可选）
    nvidia.com/gpu: "4"

weight 用于 proportion 插件按权重分配；capability 是该队列能用的资源上限；guarantee 是保底份额。注意 proportion 与 capacity 插件二选一，前者按权重、后者按显式配额。

7. 关键调度策略配置

Volcano 的策略通过 ConfigMap 中的 tiers（插件分层）与 actions（动作顺序）组合。默认配置通常包含两个 tier。

# volcano-scheduler-configmap 片段
actions: "enqueue, allocate, backfill"
tiers:
  - plugins:
      - name: priority        # 第一层：排序与抢占决策
      - name: gang
      - name: conformance
      - name: drf
      - name: proportion
  - plugins:
      - name: predicates      # 第二层：节点选择与放置
      - name: nodeorder
      - name: binpack
gang 全有或全无

分布式训练的基石。基于 PodGroup 的 minMember 判断作业是否 Ready；未 Ready 的作业通过 jobPipelineFn 占坑预留，凑齐后统一绑定。

binpack 紧凑装箱

通过 nodeOrderFn 给「已用较多」的节点打高分，把 Pod 往一起堆，减少节点碎片。对 GPU 这种离散昂贵资源尤其重要。

drf 主导资源公平

Dominant Resource Fairness，按作业「主导资源」（CPU/GPU/内存中的最大占比）排序，适合多维资源的公平分配。

preempt / reclaim 抢占与回收

preempt 在队列内按优先级抢占；reclaim 跨队列按份额把借出的资源收回。两个 Action 独立配置，配合 conformance 保护系统 Pod。

常见坑：proportion 与 capacity 插件互斥，同时启用会导致配额判定冲突；enqueue 与 preempt/reclaim 通常不同时启用；修改 Action 顺序或插件分层后必须回归测试 gang 与公平性。

8. GPU 与拓扑感知

AI 训练对「放在哪」极其敏感。Volcano 在设备与拓扑层面提供了多项原生能力。

deviceshare GPU 共享

支持 GPU 共享与 MIG 模式，让多个任务共享一张卡，提升细粒度利用率。配合 vCUDA 可实现软件层 vGPU 切分与显存隔离。

numaaware NUMA 感知

考虑 CPU NUMA 拓扑，把 Pod 绑定到内存访问最优的 NUMA 节点，降低跨 NUMA 访存开销，提升多核处理器的计算性能。

task-topology 任务拓扑

针对通信密集型应用，按任务间通信关系优化放置，把通信密集的 Pod 就近调度，减少跨节点网络开销。

network topology 网络拓扑感知

充分考虑节点间网络带宽特性，为分布式训练优化数据传输路径，显著降低通信开销、提升模型训练速度。

多架构支持：Volcano 支持 x86、Arm、鲲鹏、昇腾（Ascend）等多种架构，以及 GPU 的多种虚拟化技术（动态 MIG、vCUDA、细粒度资源控制、多容器共享、统一监控）。成熟度为 Beta/Alpha 不等，生产采用前请核对目标版本。

9. 生产实践：部署与排障

部署要点

  1. 安装：通过 Helm chart 或 kubectl apply -f volcano-development.yaml 安装，会部署 volcano-scheduler、controllers、webhooks 与 CRD。
  2. 确认调度器：作业需显式设置 schedulerName: volcano，否则仍由默认 kube-scheduler 处理，gang/队列能力不生效。
  3. 配置队列：先建 Queue 并规划权重/配额，再让作业 spec.queue 指向它；多租户场景优先 proportion 或 capacity。
  4. 调优 ConfigMap：根据负载在 tiers 中增减插件、调整 actions 顺序；改完重启 volcano-scheduler。
  5. 可观测：接入 volcano metrics 与 Dashboard，关注作业 Pending 时长、gang 成功率、队列份额、抢占/回收事件。

排障清单

现象排查方向
作业一直 Pending，Pod 起不来是否设置 schedulerName=volcano；PodGroup 是否创建；minMember 是否大于集群可满足的资源；队列是否有配额。
gang 作业卡在部分调度检查 gang 插件是否启用；jobReadyFn 判定条件；是否有足够节点满足整组资源；考虑 Binpack 减少碎片。
队列资源被挤占检查 proportion/capability 配置；是否被其他队列借用；reclaim 是否启用；conformance 是否保护了系统 Pod。
优先级不生效PriorityClass 是否正确；priority 插件是否在 tier 中；jobOrderFn 是否被其他插件覆盖（tier 顺序）。
调度器频繁重启 / 性能下降检查调度周期与快照规模；扩展点回调是否有耗时逻辑（尤其 extender HTTP）；减少不必要的插件。
经验：Volcano 的问题大多不是「功能坏了」，而是「策略没配对」。先看 schedulerName 和插件配置，再看队列配额，最后才看调度算法本身。

生态集成

Volcano 已成为批处理场景的事实标准，被主流 AI/大数据框架广泛适配：Spark、TensorFlow、PyTorch、Flink、Argo、Ray、MindSpore、PaddlePaddle、OpenMPI、Horovod、Kubeflow 等。相关子项目包括 volcano-global（多集群）、descheduler（重调度）、dashboard（可视化）。

11. 总结与面试题

核心要点回顾

  1. 存在根源是调度单元错配：K8s 以 Pod 为单位逐个调度，批处理需要以「作业 + 队列」为单位整体调度。五大痛点（死锁/无配额/难回收/碎片/拓扑）由此而来。
  2. 周期驱动而非事件驱动：每个 Session 基于快照做决策并统一提交，保证一致性与大规模批处理能力——这是实现 Gang 整体调度的前提。
  3. Action + Plugin 两层可插拔：Action 定义调度环节，Plugin 通过注册扩展点回调提供算法，策略可按 ConfigMap 灵活组合。
  4. allocate 是核心：队列→作业→任务层层排序，再经 predicates 预选、nodeorder/binpack 优选，最后绑定或 pipeline 占坑。
  5. 扩展点四大类：排序、过滤准入、抢占回收、状态预留，共 20+ 个 Fn；同一 Fn 可被多插件注册，靠 tier 顺序组合。
  6. 三种扩展方式：配置内置插件（零代码）、extender（HTTP 跨语言）、自定义 Plugin（编译进调度器）。
  7. 对比 K8s：官方是单 Pod 线性流水线（~13 扩展点），Volcano 是作业级多级回调（20+），多出的复杂度服务于 Gang、配额、抢占回收。

高频面试题

Q1 · Volcano 为什么不用事件驱动？

因为 gang「全有或全无」必须先看到全局再一次性决策。周期驱动 + 一致性快照让同周期内所有决策基于同一份「事实」，避免事件驱动下的中间态与互相打架。

Q2 · gang 是怎么实现的？

基于 PodGroup 的 minMember 判定作业是否 Ready；未 Ready 时用 jobPipelineFn 占坑预留资源，凑齐后统一绑定。核心插件是 gang，涉及 jobValid/Ready/Starving 等钩子。

Q3 · preempt 和 reclaim 区别？

preempt 是同队列内按优先级抢占；reclaim 是跨队列按权重把借出的应得份额收回。两个独立 Action，分别对应队列内公平与队列间借还。

Q4 · 扩展点为什么比 K8s 多？

不是功能堆得多，而是模型不同：K8s 是单 Pod 线性流水线（阶段卡槽），Volcano 要排 Queue→Job→Task→Node 四层，且把同类能力拆成 Order/Valid/Ready/Starving 等更细的回调。
