摘要

Volcano 是 CNCF 旗下首个、也是目前唯一的官方容器批处理调度项目。它把批处理领域的完整语义——作业（Job/PodGroup）、队列（Queue）、公平、抢占回收、拓扑感知——搬进了 Kubernetes 调度器。本文从「调度单元错配」这一根源出发，系统拆解 Volcano 的 Session + Action + Plugin 三层架构、调度全流程、插件扩展点体系，并补齐核心对象实战、关键策略配置、GPU/拓扑感知与生产排障，并新增 6 章基于 master 分支源码核实的深度展开（运行时序 / 写回链路 / 对象模型 / allocate 深挖 / gang 通俗理解 / 一次调度全景），最后给出与 kube-scheduler 的深度对比和选型建议。

阅读约定：本文在原《Volcano 调度器原理详解》基础上扩展了实战、策略配置、GPU 与生产章节。涉及 API 与特性以 Volcano v1.9+ / v1.10+ 为准；部分高级特性（如动态 MIG、volcano-global 多集群）的成熟度已在文中标注，落地前请核对目标版本文档。

0. 为什么需要 Volcano：问题与对策

理解 Volcano，先要理解它为什么存在。根源只有一句话：调度单元的错配。原生 kube-scheduler 以「单个 Pod」为单元逐个调度，这对无状态 Web 服务没问题；但批处理 / AI 训练的语义是「一组 Pod 才是一个任务」。这个错配引出五个问题，下面把每个问题与 Volcano 的对策逐条对应。

① 分布式训练「部分调度死锁」· 最核心

MPI/PyTorch DDP 需 N 个 Pod 同时启动。K8s 逐个调度：先起的 Pod 占住资源并等待通信，剩下的 Pod 因资源不足 Pending——全体卡死，谁也不释放。

→
Gang Scheduling（全有或全无）

用 PodGroup 把一组 Pod 绑成整体，minAvailable 定义最小运行数。凑不齐就一个都不调，凑齐才一起调，从根上杜绝死锁。

gang 插件 · jobValidFn / jobReadyFn / jobStarvingFn
② 多租户资源争抢、无配额

K8s 没有「作业队列」概念，Pod 直接进调度队列裸竞争。重要任务可能被海量小任务挤掉，团队之间无公平性保障。

→
多层级队列 + 配额

引入 Queue CRD（可分层），deserved/guarantee/capability 描述应得、保底、上限，按权重或显式配额分配，实现租户隔离与公平。

proportion（按权重）· capacity（显式配额）· queueOrderFn
③ 资源借还不灵活

K8s 的抢占只按 Pod 优先级，没有「跨队列回收」：A 队列借用了 B 队列的空闲资源，当 B 自己要用时却拿不回来。

→
抢占与回收分离

preempt 处理同队列内高优先级抢占；reclaim 按队列权重把「借出去」的应得份额收回来。两个独立 Action，各管一层。

preempt + reclaim Action · preemptableFn / reclaimableFn / victimTasksFn
④ 资源碎片、利用率低

默认 LeastAllocated 策略倾向把 Pod 打散，节点残留大量碎片，昂贵的 GPU 资源白白浪费。

→
装箱 + 碎片回填

binpack 把 Pod 往已用节点上紧凑堆放；backfill 用调度周期剩余碎片资源去塞 pending 的小任务，榨干每一份资源。

binpack · backfill Action · nodeOrderFn
⑤ 异构设备与拓扑感知

GPU/NPU 共享、NUMA 亲和、多机通信拓扑——AI 训练对「放在哪」极其敏感，默认调度器无能为力。

→
设备与拓扑感知插件

numaaware 考虑 CPU NUMA，deviceshare 支持 GPU 共享，task-topology / 网络拓扑感知降低跨节点通信开销。

numaaware · deviceshare · network topology aware
本质：K8s 调度的是「一个个 Pod」，Volcano 调度的是「一组组作业 + 一层层队列」。多出来的复杂度，全部服务于批处理场景的刚需：整体调度、公平配额、借还回收、高利用率、异构感知。

三个层层递进的设计支柱

① 显式建模批处理概念

用 PodGroup 把一组 Pod 绑成「作业」，用 Queue 把租户映射成「队列」——让「组」和「队列」成为调度器看得见的一等公民，而不只是外部约定。

② 周期快照 + Session

要做到「全有或全无」，必须先看到全局再一次性决策。所以 Volcano 不用事件驱动，而是每周期拉一份一致性快照，在 Session 内基于同一份「事实」做整体判断。

③ Action 时机 + Plugin 逻辑

把决策时机切细（入队/分配/抢占/回收/回填），每个时机再挂可插拔算法。扩展点之所以多，正是因为时机被切得细——这是「为什么比 K8s 多」的真正答案。

调度流程：每一步的动机

  • Cache · 准备与快照
    监听集群 → 缓存 Node / Pod / Job / Queue，拉取一致性快照。解决：分布式系统里信息难同步；用某一时刻的快照调度，保证同周期内所有决策基于同一份「事实」，不会互相打架。
  • Action 1 · enqueue 入队
    按队列配额与规则过滤 Job，状态 pending → inqueue。解决：配额准入，拦住超额作业（对应问题②多租户公平）。
  • Action 2 · allocate 分配
    队列→作业→任务层层排序，predicates 预选 + nodeorder/binpack 优选，选点绑定；凑不齐 minAvailable 则整个 Job 不调。解决：gang 全有或全无（①）、binpack 提升利用率（④）、numaaware 处理拓扑（⑤）。
  • Action 3/4 · preempt / reclaim
    preempt 同队列内高优先级抢占；reclaim 跨队列按权重回收借出的资源。解决：资源借还分两层（③），让高价值任务拿得到资源。
  • Action 5 · backfill 回填
    用本周期剩余的碎片资源，调度 pending 的小任务 / BestEffort 作业。解决：见缝插针，把利用率榨到最高（④）。
  • Apply · 提交收尾
    把本周期所有绑定/驱逐决策一次性应用到集群，关闭 Session。解决：原子性，避免「调了一半」的中间态，让调度效果可预期。

贯穿全流程的机制：每个 Action 具体怎么排序、怎么过滤、谁能抢谁，都由 Plugin 注册的扩展点回调决定——这就是 Action + Plugin 分层。

1. Volcano 是什么

Volcano 是 CNCF 旗下的、基于 Kubernetes 的高性能批处理调度引擎，也是 CNCF 首个且唯一的官方容器批处理调度项目。原生 kube-scheduler 以单个 Pod 为调度单元，难以满足 AI 训练、MPI、Spark/Flink、Ray 等场景中「一组 Pod 必须同时启动」的需求。Volcano 在 K8s 之上提供了作业级（Job/PodGroup）调度、多层级队列配额、Gang Scheduling、公平共享、抢占回收和异构设备（GPU/NPU）支持。

它的调度器 volcano-scheduler 采用高度可扩展的 Session + Action + Plugin 三层架构：每个调度周期开启一个 Session，按顺序执行多个 Action，而每个 Action 的具体算法由注册的 Plugin 提供。这种分层让调度策略完全可插拔。

A Action

定义「做什么」：enqueue / allocate / preempt / reclaim / backfill 等调度环节。

P Plugin

定义「怎么做」：通过向 Session 注册回调函数（扩展点）提供具体算法。

S Session

承载一个调度周期：基于集群快照做决策，周期结束统一提交，保证一致性。

能力全景

统一调度

支持原生 K8s 工作负载；通过 VolcanoJob 完整支持 PyTorch/TensorFlow/Spark/Flink/Ray；在线微服务与离线批处理统一调度，提升集群利用率。

丰富调度策略

Gang、Binpack、DRF、Proportion/Capacity、NodeGroup、SLA、Task-topology、NUMA-aware，以及异构设备（GPU/NPU）调度。

队列资源管理

多维资源配额（CPU/Memory/GPU）；多层级队列与资源继承；队列间借用、回收、抢占；多租户隔离与优先级。

高级能力

网络拓扑感知、在线离线混部（超卖/CPU burst）、多集群调度（volcano-global）、动态重调度（descheduler）、Dashboard 与指标。

2. 整体调度流程

Volcano 的调度决策不是事件驱动，而是周期驱动：每个周期开启一个 Session，从 Cache 拉取集群快照，遍历待调度 Job，依次执行各 Action，为 Job 找到合适节点并绑定，最后关闭 Session。

3. 插件与扩展点体系

每个 Plugin 必须实现 Name()、OnSessionOpen(ssn)、OnSessionClose(ssn) 三个方法。真正的扩展逻辑发生在 OnSessionOpen：插件在此把算法函数注册到 Session 的各类扩展点（本质是若干 Fn map），Action 执行时再回调它们。

插件接口：三个方法

Name() string

返回插件唯一名称，供 ConfigMap 配置引用。

OnSessionOpen(ssn)

每个调度周期开始时调用，在此把算法函数注册到 Session 的各个扩展点。

OnSessionClose(ssn)

会话结束时清理中间状态、更新指标。

扩展点四大类（20+ 个 Fn）

① 排序类 Ordering

jobOrderFn · queueOrderFn · taskOrderFn · nodeOrderFn · batchNodeOrderFn · bestNodeFn · namespaceOrderFn · clusterOrderFn

② 过滤与准入 Validation

predicateFn · prePredicateFn · jobEnqueueableFn · jobValidFn · jobReadyFn · jobStarvingFn

③ 抢占与回收 Preempt / Reclaim

preemptableFn · reclaimableFn · overusedFn · allocatableFn · victimTasksFn · reclaimFn

④ 状态与预留 State / Reserve

reservedNodesFn · targetJobFn · jobPipelineFn · jobEnqueuedFn · eventHandler

三种扩展方式：从易到难

A · 配置内置插件

在 ConfigMap 的 tiers 里增减/排序插件，零代码改行为。首选。

B · Extender 外部扩展

通过 HTTP 回调外部服务，钩子最全、可跨语言，无需重编译调度器。

C · 自定义 Plugin

实现 Plugin 接口 + RegisterPluginBuilder 注册，编译进自定义调度器。

机制要点：同一扩展点可被多个插件注册，结果按 tier 顺序组合——这正是默认配置分两层 plugins 的原因。例如 priority 与 gang 都注册 jobOrderFn，需靠分层顺序决定最终排序。

5. 与 K8s 官方调度器对比

Volcano 的扩展点数量（20+）明显多于 Kubernetes 官方调度框架（约 12~13 个）。但这并不是简单的「功能堆得多」，而是两种扩展模型的本质差异：官方调度器是线性流水线（Pipeline），一次只调一个 Pod，扩展点是主线上固定的阶段卡槽；Volcano 是多级决策回调（Hook），一次调一批 Job，扩展点是 Action 回调的各种决策函数。

◆ kube-scheduler · 线性流水线

一次只调一个 Pod；扩展点 = 主线上固定的「阶段卡槽」，约 12~13 个。

  • QueueSort → PreFilter → Filter → PostFilter
  • PreScore → Score → NormalizeScore
  • Reserve → Permit → PreBind → Bind → PostBind

▲ Volcano · 多级决策回调

一次调一批 Job；扩展点 = Action 回调的「决策函数」，20+ 个 Fn（四大类）。

  • jobOrderFn / queueOrderFn / taskOrderFn
  • predicateFn / jobValidFn / jobReadyFn
  • preemptableFn / victimTasksFn / reclaimableFn…

1 · 调度对象层级

K8s 只围绕 Pod 一个层级；Volcano 要同时排 Queue→Job→Task→Node 四层，每层都要排序/判断，钩子自然翻倍。

2 · 模型粒度不同

K8s 是「阶段卡槽」，一个阶段一个接口；Volcano 是「决策回调」，同类能力拆成 Order/Valid/Ready/Starving 等更细的 Fn。

3 · 功能内建范围

gang、DRF、配额、抢占回收、资源预留都是 Volcano 原生能力；K8s 多交给 out-of-tree 插件（如 Coscheduling / Kueue）。

一句话总结：K8s 用「少而固定的阶段」换取简洁，Volcano 用「多而细的回调」换取批处理场景的可控性——这是为 Gang 调度、多租户配额、抢占回收这些批处理刚需付出的复杂度代价。

6. 核心概念与 YAML 实战

三个核心对象

Job（VCJob）

Volcano 自定义 CRD，描述一个批处理作业：多个 Task、每个 Task 的副本数、生命周期策略。是对原生 Job 语义的扩展。

PodGroup

gang 调度的载体，绑定一组 Pod，声明 minMember / minTaskMember。原生 Job/Deployment 也可通过标签关联 PodGroup。

Queue

租户/队列的抽象，可分层。通过 weight 或 capability / guarantee 描述资源份额，是公平与配额的基础。

实战一：一个 Gang 调度的 VCJob

apiVersion: batch.volcano.sh/v1alpha1
kind: Job
metadata:
  name: pytorch-ddp
spec:
  minAvailable: 4            # 凑齐 4 个 Pod 才一起启动（gang）
  schedulerName: volcano
  queue: research-queue
  plugins:
    env: []
    svc: []
  tasks:
    - name: worker
      replicas: 4
      template:
        spec:
          containers:
            - name: pytorch
              image: pytorch/pytorch:2.1.0-cuda12.1-cudnn8-runtime
              command: ["python", "train.py"]
              resources:
                limits:
                  nvidia.com/gpu: 1
      policies:
        - event: PodEvicted
          action: RestartJob

minAvailable: 4 是 gang 的关键：Volcano 会为这 4 个 Pod 预留资源，凑不齐就一个都不绑定，从根本上避免「3 个 GPU 占着空等第 4 个」的死锁。

实战二：队列配额

apiVersion: scheduling.volcano.sh/v1beta1
kind: Queue
metadata:
  name: research-queue
spec:
  weight: 2                  # 按权重参与 proportion 分配
  capability:                # 资源上限
    nvidia.com/gpu: "16"
    cpu: "64"
  guarantee:                 # 保底份额（可选）
    nvidia.com/gpu: "4"

weight 用于 proportion 插件按权重分配；capability 是该队列能用的资源上限；guarantee 是保底份额。注意 proportion 与 capacity 插件二选一，前者按权重、后者按显式配额。

7. 关键调度策略配置

Volcano 的策略通过 ConfigMap 中的 tiers（插件分层）与 actions（动作顺序）组合。默认配置通常包含两个 tier。

# volcano-scheduler-configmap 片段
actions: "enqueue, allocate, backfill"
tiers:
  - plugins:
      - name: priority        # 第一层：排序与抢占决策
      - name: gang
      - name: conformance
      - name: drf
      - name: proportion
  - plugins:
      - name: predicates      # 第二层：节点选择与放置
      - name: nodeorder
      - name: binpack
gang 全有或全无

分布式训练的基石。基于 PodGroup 的 minMember 判断作业是否 Ready；未 Ready 的作业通过 jobPipelineFn 占坑预留，凑齐后统一绑定。

binpack 紧凑装箱

通过 nodeOrderFn 给「已用较多」的节点打高分，把 Pod 往一起堆，减少节点碎片。对 GPU 这种离散昂贵资源尤其重要。

drf 主导资源公平

Dominant Resource Fairness，按作业「主导资源」（CPU/GPU/内存中的最大占比）排序，适合多维资源的公平分配。

preempt / reclaim 抢占与回收

preempt 在队列内按优先级抢占；reclaim 跨队列按份额把借出的资源收回。两个 Action 独立配置，配合 conformance 保护系统 Pod。

常见坑：proportion 与 capacity 插件互斥，同时启用会导致配额判定冲突；enqueue 与 preempt/reclaim 通常不同时启用；修改 Action 顺序或插件分层后必须回归测试 gang 与公平性。

8. GPU 与拓扑感知

AI 训练对「放在哪」极其敏感。Volcano 在设备与拓扑层面提供了多项原生能力。

deviceshare GPU 共享

支持 GPU 共享与 MIG 模式，让多个任务共享一张卡，提升细粒度利用率。配合 vCUDA 可实现软件层 vGPU 切分与显存隔离。

numaaware NUMA 感知

考虑 CPU NUMA 拓扑，把 Pod 绑定到内存访问最优的 NUMA 节点，降低跨 NUMA 访存开销，提升多核处理器的计算性能。

task-topology 任务拓扑

针对通信密集型应用，按任务间通信关系优化放置，把通信密集的 Pod 就近调度，减少跨节点网络开销。

network topology 网络拓扑感知

充分考虑节点间网络带宽特性，为分布式训练优化数据传输路径，显著降低通信开销、提升模型训练速度。

多架构支持：Volcano 支持 x86、Arm、鲲鹏、昇腾（Ascend）等多种架构，以及 GPU 的多种虚拟化技术（动态 MIG、vCUDA、细粒度资源控制、多容器共享、统一监控）。成熟度为 Beta/Alpha 不等，生产采用前请核对目标版本。

9. 生产实践：部署与排障

部署要点

  1. 安装：通过 Helm chart 或 kubectl apply -f volcano-development.yaml 安装，会部署 volcano-scheduler、controllers、webhooks 与 CRD。
  2. 确认调度器：作业需显式设置 schedulerName: volcano，否则仍由默认 kube-scheduler 处理，gang/队列能力不生效。
  3. 配置队列：先建 Queue 并规划权重/配额，再让作业 spec.queue 指向它；多租户场景优先 proportion 或 capacity。
  4. 调优 ConfigMap：根据负载在 tiers 中增减插件、调整 actions 顺序；改完重启 volcano-scheduler。
  5. 可观测：接入 volcano metrics 与 Dashboard，关注作业 Pending 时长、gang 成功率、队列份额、抢占/回收事件。

排障清单

现象排查方向
作业一直 Pending，Pod 起不来是否设置 schedulerName=volcano；PodGroup 是否创建；minMember 是否大于集群可满足的资源；队列是否有配额。
gang 作业卡在部分调度检查 gang 插件是否启用；jobReadyFn 判定条件；是否有足够节点满足整组资源；考虑 Binpack 减少碎片。
队列资源被挤占检查 proportion/capability 配置；是否被其他队列借用；reclaim 是否启用；conformance 是否保护了系统 Pod。
优先级不生效PriorityClass 是否正确；priority 插件是否在 tier 中；jobOrderFn 是否被其他插件覆盖（tier 顺序）。
调度器频繁重启 / 性能下降检查调度周期与快照规模；扩展点回调是否有耗时逻辑（尤其 extender HTTP）；减少不必要的插件。
经验：Volcano 的问题大多不是「功能坏了」，而是「策略没配对」。先看 schedulerName 和插件配置，再看队列配额，最后才看调度算法本身。

11. 运行时序：快照、串行与周期

前面讲的是「调度做什么」，这一章回答「调度怎么跑」。两个核心事实常被误解：一次调度是否同时考虑所有任务，以及多个调度周期是否并发。答案是：数据上把全部任务读入快照，决策上逐 Action 筛选；而 Session 严格串行，默认每轮结束后再等 1 秒。

  • ① Snapshot() 全量快照（数据层：全部可见）
    ssn.Jobs / ssn.Nodes / ssn.Queues = snapshot.X 整体引用赋值、无过滤；Task 随 JobInfo 进入。时间维度：快照在每个调度周期开始时拍下，整个 Session 内不再刷新——一次性一致视图，非实时数据。
  • ② enqueue → allocate 主分配
    只看 inqueue、JobValid 通过、有资源请求的 Job/Task；gang 在此做 minAvailable 全有全无判定。成功者状态变更、节点资源被占用。
  • ③ preempt → reclaim 抢占回收
    只处理被抢占 / 被回收的具体任务，改变资源归属；范围更窄，依赖前面是否已产生 Pending 任务。
  • ④ backfill 碎片回填（只挑无请求任务）
    源码 if task.HasSchedulingResourceRequests() { continue }：只要有资源请求就跳过，只留 Pending/Pipelined 的无请求（BestEffort）任务，填前面分完后的剩余碎片。
    • 数据上是、决策上不是：一次 Session 把所有任务读进快照，但没有哪个 Action 会「考虑所有任务」。backfill 尤其特殊——它压根不调度正经作业，只捡被前面跳过的无请求边角料，且用的是前面分完后剩余的资源。

    串行调度周期：单 goroutine，跑完再等 1 秒

    单一调度循环 wait.Until(pc.runOnce, schedulePeriod, stopCh) —— 单 goroutine 同步调用，Session 严格串行、不重叠。一个 Session 内部：OpenSession → enqueue → allocate → preempt → reclaim → backfill → CloseSession（串行的 for 循环，共用同一 ssn）。

    Session #N
    ① 快照 ② Actions ③ Close
    ≈1s→
    Session #N+1
    ① 快照 ② Actions ③ Close
    +1s→
    …
    串行不重叠
    默认 1 秒、跑完再等：周期默认 defaultSchedulerPeriod = time.Second（启动参数 --schedule-period）。wait.Until 采用 sliding 计时——从本轮结束后才开始算 1 秒，所以真实周期 ≈ 本轮耗时 + 1 秒，调度慢不会并发追赶。注意区分：调度决策串行，但 Cache 的 informer / worker（NodeWorkerThreads=20 等）是并发更新数据的，只是不参与决策。生产多副本通过 leader election 保证全局只有一个 active 实例在调度。

    12. 结果落地：绑定与驱逐

    调度决策做完，怎么在真实集群生效？两个关键认知：Volcano 从不创建 workload——Pod 早已由 controller 建好，scheduler 只给它们选节点；写回靠的是实打实的 K8s API 调用（创建 Binding 对象 / 删除 Pod），而且是异步的，不在 Session 内同步完成。

    绑定写回链路：Session 提交 → Binding 对象 → kubelet

  • ① Session 决策（内存态）：只记录决策，不写 API
    Statement.Allocate() 设 task.Pod.Spec.NodeName = hostname 并加入 operations——纯内存，gang 不过就 Discard 回滚。
  • ② Commit：入队而非直接写
    Commit() → allocate() → CreateBindContext() → cache.AddBindTask()，丢进 BindFlowChannel（容量 5000）。此时仍未调用 API Server。
  • ③ Cache 后台（异步）：每 20ms 消费
    wait.Until(processBindTask, 20ms) → BindTask() 起 goroutine → 先跑 PreBind 插件 → 再 Binder.Bind()。批量大小默认 1，可用 BATCH_BIND_NUM 调。
  • ④ API Server：真正写回——创建 Binding 对象
    Pods(ns).Bind(&v1.Binding{Target: Node/xxx})。不是 Update/Patch 的 spec.nodeName，而是 POST 一个 Binding 子资源（与 kube-scheduler 一致）。成功后记「Scheduled」事件。
  • ⑤ kubelet 接手
    API Server 把 nodeName 落库，目标节点 kubelet watch 到并启动容器。调度器的活到此结束。
    • 内存设值 ≠ 落库：内存里的 Spec.NodeName 只用于决策和 cache 记账；真正改变集群状态的是那次 Binding POST。bind 失败会回滚 PreBind 并把任务重新入队重调。

    驱逐写回链路：改 cache 只是记账，Delete API 才生效

  • ① Session 内（内存态）：只记账不删
    Statement.Evict() 把 task 改为 Releasing、更新 node 记账、加入 operations。gang/抢占判定失败就 Discard 回滚。
  • ② Commit → Cache：改 cache + 起 goroutine
    cache.Evict() 标记 Releasing、记 PodGroup 的 Evict 事件，然后 go sc.Evictor.Evict(p, reason)。返回 nil 只代表入队成功。
  • ③ defaultEvictor（真实生效）：真正删 Pod
    先 UpdateStatus 打上 PodReady=False 和 DisruptionTarget=True(PreemptionByScheduler)，再 Pods(ns).Delete(p.Name) —— 这一步才真正删除集群里的 Pod。
  • ④ Controller（重建）连锁反应
    Pod 被删 → ReplicaSet / vc-controller 发现副本不足 → 创建新 Pod（Volcano 自己不重建）→ Pending → 下一轮 Session 重调，此时资源已被高优先级任务占用。
    • PDB 注意：preempt 与 reclaim 走同一条路（都是 Evict，区别只在范围和 reason）。但默认 evictor 直接 Delete、没走 policy/v1 的 Eviction subresource，因此不会自动做 PDB 校验，对有 PDB 保护的业务要留意。失败会 resyncTask 重新入队。

    allocate 与 preempt / reclaim 的协作关系

    allocate（独立 Action）

    只用空闲资源、全程无 Evict：Statement 只有 Pipeline/Allocate，代码里无任何 Evict 调用。gang 的 JobReady 通过才 Commit，资源不够就直接放弃这个 job，不驱逐别人。

    Session 传递（交接）

    allocate 的产物 = preempt 的输入：仍缺资源的 job 保持饥饿态，preempt 用 if !ssn.JobStarving(job) { continue } 筛出它们；allocate 标注的不可调度节点也被 preempt 复用。

    判断逻辑在抢占 Action 内部：preempt/reclaim 自己判断 + 自己闭环（同一 Statement 事务）——选 victim → nodeStmt.Evict(victim) → preemptorFitsOnNode() 检查资源 → 够则 nodeStmt.Pipeline(preemptor)。驱逐和占位在同一 Statement 里一起 Commit；没达到 JobPipelined 就整体 Discard 回滚。三者串在同一 Session、共用一份快照，看起来像「allocate 的补救」，但代码上是平级 Action。进阶：gangpreempt/gangreclaim 会锁定节点（NominatedHyperNode），下一轮 allocate 走 allocateFromNomination 快速兑现。

    13. 对象模型：从提交到调度单元

    前面反复提到 Queue / Job / Task 三层，这里回答它们的来源：层级不是调度器运行时把散装 Pod「聚合」出来的，而是提交时就定义好的对象模型。用户提交 VCJob（作业），其中声明 queue、minAvailable、各 task 的 replicas；vc-controller 据此展开成 PodGroup + 多个 Pod，并把三层关联写进 Pod 的 annotation。

  • ① 用户提交：VCJob（batch.volcano.sh/v1alpha1 的 Job CRD）
    spec.queue 声明归属队列，minAvailable: 8 是 gang 约束，tasks[].replicas: 8 展开成 8 个 Pod。Queue 是独立 CRD，管理员提前建好。
  • ② controller 创建：1 个 PodGroup + N 个 Pod
    PodGroup 的 MinMember = minAvailable 把 8 个 Pod 绑成一个 gang 单元；每个 Pod 带 annotation：KubeGroupNameAnnotationKey → PodGroup，QueueNameKey → Queue。
  • ③ 快照 → allocate 逐层 pop
    Pop Queue（查 Overused）→ Pop Job/SubJob（查 JobReady）→ Pop Task（predicate + nodeOrder）。
  • ④ node.AddTask 扣减内存资源
    Idle.sub / Used.Add；Pipeline 则是 Pipelined.Add 软预留（FutureIdle = Idle + Releasing − Pipelined）。类似 K8s Reserve 的作用，但不是独立扩展点——直接在 NodeInfo 里改字段；Session 结束即丢弃，真正持久化靠 Binding 写回后的真实 Pod。
    • apiVersion: batch.volcano.sh/v1alpha1
kind: Job                 # ← 这就是「作业」
metadata:
  name: pytorch-ddp
spec:
  queue: training         # ← 提交时声明归属队列
  minAvailable: 8         # ← gang 约束 → PodGroup.MinMember
  tasks:
  - name: worker
    replicas: 8           # ← 展开成 8 个 Pod
    template: ...
    对象三层与提交字段的对应
    层级K8s 对象谁创建提交里怎么指定
    队列Queue CRD管理员提前建spec.queue 声明归属
    作业VCJob + PodGroup你提交 Job；controller 造 PodGroupminAvailable → MinMember
    任务Podcontroller 按 replicas 展开replicas: 8 → 8 个 Pod

    一句话：提交 Job（声明 queue/replicas/minAvailable）→ controller 造 PodGroup + Pod → Session 快照 → allocate 逐层 pop → AddTask 扣内存资源 → Commit 后异步 Binding 落库。

    Queue：内置队列与三级资源模型

    安装后自动创建 root（根队列）与 default（默认队列 weight=1，VCJob 没写 spec.queue 就落这里），均不可改删；其余按业务自建。核心是三级配额模型：guarantee ≤ deserved/weight ≤ capability。

    guarantee 硬下限

    独占预留，其他队列不能用。

    deserved / weight 软基准

    应得份额；空闲可借出、繁忙可回收；二者互斥。

    capability 硬上限

    绝对封顶，再空闲也不能超。

    另有 priority（分配/抢占优先级）、reclaimable（超额能否被回收，默认 true）、parent（分层父队列）、state（仅 Open 可接收任务）。Kubeflow 等框架无 spec.queue，改用注解 scheduling.volcano.sh/queue-name + spec.schedulingPolicy.{queue,minAvailable}。

    capacity 与 proportion 二选一：capacity（配 deserved）与 proportion（配 weight）不能同时启用。动态扩缩容集群适合 proportion（自动重算 deserved），精细控制 GPU 等资源适合 capacity；官方 v1.9+ 推荐 capacity。提交后准入组件校验队列是否存在、state 是否 Open；分层队列还要求叶子节点。
    apiVersion: scheduling.volcano.sh/v1beta1
kind: Queue
metadata:
  name: training
spec:
  deserved:                    # 应得份额（可借出 / 可回收）
    cpu: "16"
    nvidia.com/gpu: "8"
  guarantee:                   # 独占预留
    resource:
      cpu: "8"
      nvidia.com/gpu: "2"
  capability:                  # 硬上限
    cpu: "32"
    nvidia.com/gpu: "16"
  priority: 100
  reclaimable: true

    14. allocate 深挖：层级决策与资源记账

    这一章把最核心的 allocate 拆开，并回答三个此前一笔带过的问题：allocate 内部到底做了哪几件事、为什么按队列→作业→任务分级、Session 里装的什么、整体决策后如何开启 Binding。以下均基于 master 分支源码核实。

    allocate 内部四件事

  • 0 · 准备：筛选谁有资格被分配（buildAllocateContext）
    跳过 pending、JobValid 不通过、被 unschedulable 抑制、队列不存在的 job；organizeJobWorksheet 分 nominated（上轮抢占锁定）与 regular 两阶段；无资源请求的 task 直接跳过，留给 backfill。
  • 1 · 三层决策循环：固定六步
    QueueOrderFn → JobOrderFn → TaskOrderFn → predicate 过滤 → nodeOrderFn 打分 → Allocate/Pipeline。
  • 2 · 单 task 动作（allocateResourcesForTasks）
    配额检查 Allocatable + PrePredicateFn；预选 predicate（resourcefit + predicates）；优选 prioritizeNodes 分两梯度——Idle 就够的节点优先，其次 FutureIdle（Idle+Releasing−Pipelined）才够的节点。空闲够 → stmt.Allocate()；只有 FutureIdle 够 → stmt.Pipeline() 占坑。
  • 3 · gang 判定与事务提交（最关键）
    if stmt != nil && ssn.JobReady(job) { stmt.Commit() } —— 满足 gang 才提交，不满足整体 Discard 回滚。这就是 Gang 死锁不再发生的机制：要么整组全部分到，要么一个都不占。
    • allocate 不做的事同样重要：不写 API Server（只内存决策 + Statement 记账）；不驱逐任何 Pod（Statement 只有 Pipeline/Allocate，资源不够就放弃，交给 preempt/reclaim）。但会处理 NominatedNodeName、HyperNode 拓扑、shard 分片、FitErrors 追踪等高级细节。

    为什么按「队列 → 作业 → 任务」分级

    层级决策问题排序/判定若扁平化会怎样
    L1 队列 Queue谁先用资源？租户间公平QueueOrderFn，判 Overused；proportion/capacity没配额概念，某部门大作业吃光集群
    L2 作业 Job这一组能不能一起上？Gang 原子性JobOrderFn，判 JobReady(minAvailable)；gang/priority/drf无 gang 判定，8 卡训练全体死锁
    L3 任务 Task每个 Pod 放哪个节点？放置效率TaskOrderFn，predicate + nodeOrder；predicates/nodeorder/binpack亲和性、GPU/NUMA、装箱全失效
    分层的根本原因：公平（Queue）、原子性（Job）、放置（Task）是三种不同粒度的决策，minAvailable 是 Job 属性、配额是 Queue 属性、节点匹配是 Pod 属性，无法压成一层。且顺序必须从粗到细——先定归属，才能做 gang 整组回滚。queues.Push(queue) / jobs.Push(job) 把队列/作业压回优先级队列，下一轮按最新资源占用重算优先级，资源在队列间轮转流动——这是分层才能实现的跨租户公平。

    Session 解剖 & 从整体决策到 Binding

    ① Session = 一个调度周期的内存世界

    快照数据：Jobs/Nodes/Queues/NamespaceInfo/HyperNodes/TotalResource（⚠ 没有独立 Tasks 字段——Task 嵌在 JobInfo 里）。
    插件函数表（初始空 map）：queueOrderFns / jobOrderFns / predicateFns / jobReadyFns… 30+ 个插件在 OnSessionOpen 里注册算法。
    客户端与状态：kubeClient / vcClient / cache / recorder；Statement 不持有，用 ssn.Statement() 现场造。

    ② 整体判定，逐条记账

    「选择」是整体的：Queue→Job→Task 逐层 Pop，gang 不通过整个 Statement Discard。「产物」是逐 task 的：operations[] 每条 = operation{name, task}，类型只有 Evict/Pipeline/Allocate；Allocate 时内存里设 Pod.Spec.NodeName、状态置 Allocated（不写 API）。

    ③ gang 通过后：stmt.Commit() 遍历 operations → case Allocate: s.allocate(task) → CreateBindContext（状态置 Binding）→ cache.AddBindTask 入 channel。── 异步边界 ── BindFlowChannel → processBindTask → Binder.Bind(PreBind) → Pods().Bind() 创建 Binding 写 API Server。

    整体决策与逐 Pod 绑定并不矛盾：整体判定保 gang 原子性，逐 task 记账保执行单位；Commit 把每条 Allocate 逐个转成 BindTask 入队，后台异步为每个 Pod 创建 Binding。

    15. 通俗理解：Gang 与决策单位

    前面几章偏机制细节，这一章用大白话把两个最容易被问到的点讲透：Gang 调度到底怎么保证「全有或全无」、allocate 一次决策的单位究竟是一组 Pod 还是单个 Pod。

    Gang 调度通俗版：「8 人聚餐订位」

    一句话：把一组 Pod 当成「一单生意」——凑得齐就整单成交，凑不齐就整单作废，绝不做一半。8 卡训练要 8 个 Pod 同时起来互相通信，就像 8 个人吃饭必须坐一桌。

    ❌ K8s 默认：来一个安排一个

    • 先到 4 人 → 坐了 4 个座位占着不走
    • 后到 4 人 → 没整桌，永远等不到位
    • 先到的 4 人 → 等同伴，不肯让座
    • 结果：全体卡死，座位（GPU）白占着

    ✅ Volcano Gang：凑不齐全撤回

    • ① 绑成一单：PodGroup + minAvailable:8
    • ② 先看全貌：拍资源快照，看清总共剩几张卡
    • ③ 试算+撤回：内存里分一个问一次「够 8 了吗」，JobReady 通过才整体 Commit；不够就 Discard 全撤回，一个不占
    为什么撤回不留痕迹：整个试算都在 Session 内存里进行，NodeName 只是内存对象，gang 不通过就 Discard 回滚——没碰 API Server，所以不存在「占了又放」的副作用。三招记忆：先绑成一单（PodGroup）+ 看全貌（快照）+ 凑不齐全撤回（JobReady 才 Commit）。

    allocate 的决策单位：整体决策，逐 Pod 选点

    PodGroup
    决策单位 · 整组 Commit/Discard
    单个 Pod
    节点选点 · predicate + nodeOrder

    结论：allocate 的决策单位是一个 PodGroup（作业），不是单个 Pod。但一轮会处理多个 PodGroup——「一次遍历多组、逐个组决策」。要分清「决策单位」与「执行单位」。

    for {
  queue := queues.Pop()   // 弹出一个队列
  job := jobs.Pop()       // 弹出该队列里的一个作业(PodGroup)
  // → 组内每个 task 逐个选节点
  // → JobReady(job)：整组 Commit 还是 Discard
  queues.Push(queue)      // 队列重新入队
}
    维度单位说明
    决策判定一个 PodGroupJobReady 针对整组；gang 不满足整组 Discard
    节点选点单个 Pod组内逐个 task 做 predicate + nodeOrder（物理上一次只能放一个）
    结果提交一个 PodGroup整组 Operation 放同一个 Statement，一起 Commit/Discard
    为什么不能像 K8s 那样以单 Pod 为单位：每分一个 Pod 就立刻绑定 → Pod 互不相关 → 「4 个起来、4 个卡住」死锁。Volcano 让组内 Pod 逐个选节点但不立刻绑定，先记在同一个 Statement，整组试算完再决定一起提交或整组回滚——这就是 Gang 的落点。

    16. 一次调度全景：纵向流程与横向泳道

    17. 总结与面试题

    核心要点回顾

    1. 存在根源是调度单元错配：K8s 以 Pod 为单位逐个调度，批处理需要以「作业 + 队列」为单位整体调度。五大痛点（死锁/无配额/难回收/碎片/拓扑）由此而来。
    2. 周期驱动而非事件驱动：每个 Session 基于快照做决策并统一提交，保证一致性与大规模批处理能力——这是实现 Gang 整体调度的前提。
    3. Action + Plugin 两层可插拔：Action 定义调度环节，Plugin 通过注册扩展点回调提供算法，策略可按 ConfigMap 灵活组合。
    4. allocate 是核心：队列→作业→任务层层排序，再经 predicates 预选、nodeorder/binpack 优选，最后绑定或 pipeline 占坑。
    5. 扩展点四大类：排序、过滤准入、抢占回收、状态预留，共 20+ 个 Fn；同一 Fn 可被多插件注册，靠 tier 顺序组合。
    6. 三种扩展方式：配置内置插件（零代码）、extender（HTTP 跨语言）、自定义 Plugin（编译进调度器）。
    7. 对比 K8s：官方是单 Pod 线性流水线（~13 扩展点），Volcano 是作业级多级回调（20+），多出的复杂度服务于 Gang、配额、抢占回收。

    高频面试题

    Q1 · Volcano 为什么不用事件驱动？

    因为 gang「全有或全无」必须先看到全局再一次性决策。周期驱动 + 一致性快照让同周期内所有决策基于同一份「事实」，避免事件驱动下的中间态与互相打架。

    Q2 · gang 是怎么实现的？

    基于 PodGroup 的 minMember 判定作业是否 Ready；未 Ready 时用 jobPipelineFn 占坑预留资源，凑齐后统一绑定。核心插件是 gang，涉及 jobValid/Ready/Starving 等钩子。

    Q3 · preempt 和 reclaim 区别？

    preempt 是同队列内按优先级抢占；reclaim 是跨队列按权重把借出的应得份额收回。两个独立 Action，分别对应队列内公平与队列间借还。

    Q4 · 扩展点为什么比 K8s 多？

    不是功能堆得多，而是模型不同：K8s 是单 Pod 线性流水线（阶段卡槽），Volcano 要排 Queue→Job→Task→Node 四层，且把同类能力拆成 Order/Valid/Ready/Starving 等更细的回调。
